## Dimaloka architecture
- SEO reports use an admin-checked server function for published inventory; unconnected Google metrics remain null, never inferred from publication or sitemap counts.
- AIO articles ground Markdown links in the current published-product/active-service catalog and revalidate before saving. Covers use an admin-authenticated streaming image route, upload completed images to private media storage, and retain editable article/cover state before explicit publication.
- AI token limits share client-safe constants with server validation; all AI settings editors preserve the existing token budget when changing other settings to avoid resetting generation limits.
- Admin settings must finish loading successfully before editing/saving; admin article mutations invalidate list/detail caches so navigation never shows stale saved data.
- AI SEO uses admin-checked server functions and a fixed DollarDesa endpoint with an environment-only credential; only nonsecret model/enabled settings are stored. A shared editable recommendation editor applies metadata only on explicit action, with content replacement opt-in; article forms still require Save, and status/slug/keyword remain unchanged.
- Opted-in service HTML revisions from the category description replace the public editorial intro and feed its Service schema; metadata-only changes preserve visible copy. Saved SEO is read back and linked to its exact published page.
- Public leaf routes derive metadata and JSON-LD through `src/lib/structured-data.ts` from current loader/admin content; services use Service/Offer, never invented ratings, and private transactional pages remain noindex without public entity schema.
- Homepage presentation is normalized in src/lib/homepage.ts from the homepage_page site_settings document; its admin editor lives inside Halaman Layanan, while products, services, articles, and testimonials retain their existing management sources.
- Public service URLs use /layanan with permanent redirects from /kategori; service search reads published products through a public server function and uses a shared browser-safe matcher to keep results consistent.
- Format display dates in Asia/Jakarta explicitly so SSR and browser output agree.
- Root network-error recovery reloads the document once per failed page and clears its retry marker after successful rendering, so failed loader/query caches cannot trap the preview in an error boundary.
- Public pages read data through `src/lib/public.functions.ts` (publishable-key server client) so SSR/SEO works; admin pages under `src/routes/_authenticated/admin/` use the browser client with RLS (admin via `has_role`).
- The first account that signs up is auto-granted `admin` by the `handle_new_user` trigger; later accounts are buyers. Roles live only in `user_roles`.
- SEO publish rules are enforced both in `src/lib/seo.ts` (UI) and by DB triggers; invoice numbers are generated by a DB trigger.
- Media bucket is private (workspace blocks public buckets); uploads store 10-year signed URLs.
- Payment-stage invoices preserve contract items separately from the current amount due; linked settlement invoices require a paid DP and database validation to prevent double billing or mismatched balances. Shared payment calculations live in `src/lib/invoice-payments.ts` so public, admin, and buyer views agree.
- Category-specific service presentations use dedicated site components selected by category slug; keep the generic category listing unchanged and source visible service prices from loader data.

- Service landing pages and portfolios are keyed by category slug in `src/lib/services.ts` (site_settings docs `service_<slug>`, `portfolio_<slug>`, Website keeps `portfolio_page`, master `portfolio_master`) with in-code dummy defaults, so admin edits, master cards, and service sections stay in sync; portfolio SEO is validated in UI and DB.- Website checkout runs through `createCheckout` in `src/lib/checkout.functions.ts`: prices come from the stored product via `checkoutQuote` (src/lib/checkout.ts), and the order + invoice are written server-side; a DB trigger moves orders to paid and logs a progress update when an invoice is marked paid.
- AIO module (`/admin/aio`): admin-checked server functions call DollarDesa using the shared prompt library. Draft saving remains separate from explicit SEO-validated publication; direct product implementation targets an existing product to preserve prices/packages/URLs, and service content uses the public editorial revision path to preserve images and page structure. Mutations read back saved values and invalidate admin/public caches.
